## Guard Modeが拒否を正しく報告するよう修正

Guard mode (`--guard`)の根本的な欠陥により、拒否されたツール呼び出しが成功として報告されていました。システムは拒否メッセージに`error:`プレフィックスを確認していましたが、ほとんどの拒否にはこれが含まれていませんでした。このため、デスクトップフレーム、ステップログ、ドリフト検出の3つの重要な画面で、実際には危険なアクションがブロックされていたにも関わらず、実行成功として表示されていました。モデルはforce pushのような実際には発生しなかったアクションを自信を持って完了報告していました。現在では、すべての画面で拒否が適切にフラグ付けされ、guardの決定によるものであることが明確に示されます。

## スクリプトとドキュメント向けルールエンジンの修正

ルールエンジンには2つの相反する問題がありました。改行エスケープがルールパターンの単語境界検出を破壊していたため、複数行スクリプトは常に通過していました。一方、ブロックされたコマンドを引用しているドキュメントが誤ってハードブロックされていました。保護機能は完全に逆方向に動作しており、実際のスクリプトはルールを回避し、ドキュメントが誤検知を引き起こしていました。これらの解析問題により、2つのルールは一度も発動していませんでした。現在では補間が境界を正しく保持します。

## 監査システムの全面改修

3つの監査問題が解決されました。第一に、認証情報を検出するシステムが、そのままの状態で監査ログに保存していました。第二に、並行書き込みが監査チェーンの暗号検証を破損する可能性がありました。第三に、セキュリティUIは、並行書き込み中のハッシュチェーンリセットにより、改ざんを誤って報告していました。現在では、認証情報は監査保存前に編集され、書き込み時に一貫したチェーン状態が維持されます。

## Observe Modeが実際に観測するように修正

`observe`モードは、測定のみを行うと主張しながらルールを適用していました。ハードブロックは承認者相談前にトリガーされ、その後ロールアウト決定に使用される拒否カウントから除外されていました。33回の実際の呼び出しのうち、8回の拒否がゼロとして表示されていました。これらの拒否は残ります（明確なシグナルです）が、現在では適切にカウントされ、その発生源が特定されます。

## Kernel Visibilityが復元

トラストカーネルの判断が、実行、バッチ、ターンのHTTPエンドポイントに到達していませんでした。force push承認のような重要な決定が不可視に行われていました。現在、`CHIMERA_GOVERNANCE`が有効な場合、カーネルはすべてのHTTPフローに参加します。サーバーサイドプロンプトはHTTP接続に表示されなくなり、それらを見る人が実際にリクエストを行ったことが保証されます。

修正を適用するには`chimera upgrade`を実行してください。guard modeを使用している場合はすぐに更新してください - 以前のバージョンのレポートは危険なほど誤解を招くものでした。[Chimera Agent v0.47.0](https://github.com/brcampidelli/chimera-agent/releases/tag/v0.47.0)にすべての変更が詳細されています。

本番環境では、governed `write_file`呼び出しからの認証情報漏洩について監査ログを確認してください。修正された境界検出に対応するために、ルールファイル内の複数行スクリプトに調整が必要かどうか確認してください。
