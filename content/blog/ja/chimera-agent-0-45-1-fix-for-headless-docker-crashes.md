## Dockerコンテナが起動時にクラッシュした原因

Chimera Agent 0.45.0では、ヘッドレスDockerデプロイメントにおいてサイレント障害が発生していました。コンテナイメージは`desktop`エクストラなしで`.[full]`をインストールしますが、これは意図的にFastAPIを除外するものです。しかし、cronパスが`chimera.api.usage`をインポートし始め、APIモジュールの積極的な初期化を引き起こしました。これにより、JSONLリーダーを介して間接的にFastAPIが依存関係として引き込まれ、コンテナが`ModuleNotFoundError`でクラッシュループする原因となりました。

このバグが検出されなかった理由:
1. 開発環境では通常FastAPIがインストールされていた
2. 2,945件の既存テストのいずれもクリーンな`.[full]`インストールをシミュレートしていなかった
3. 障害は本番デプロイメントでのみ顕在化した

## コア依存関係の遅延ロード

修正は症状を隠すのではなく、根本原因に対処しています。イメージに`desktop`を追加すれば動作しましたが、エクストラのドキュメント記載の目的（"コアCLI/ゲートウェイはこれを必要としない"）に反し、不必要にイメージサイズを増加させていました。

v0.45.1では`chimera/api/__init__.py`を以下のように変更:
- 再エクスポートを積極的ではなく遅延解決する
- FastAPI依存関係をWeb固有コンポーネントに隔離する
- `desktop`が実際に必要な場合の明確な障害モードを維持する

5つのリーフモジュール（`usage`、`roles`、`sessions`、`posture`、`config_api`）は、CLI操作でインポートされても暗黙的にWebスタックを引き込まなくなりました。ゲートウェイは`.[full]`インストールのみで機能するようになっています。

## 新しい安全策

FastAPIが利用できない状態でもインポートが機能することを検証するサブプロセステストを追加しました。これは以下を行うことでリリース前に問題を検出できたはずです:
1. `fastapi`を意図的にインポート不可にした環境で実行
2. 他のチェックに進む前にコア機能を確認
3. 実際のデプロイメント条件を反映

エンドツーエンド検証により修正を確認: クリーンな`.[full]`インストールで`serve --cron`がクラッシュせずに実行できるようになりました。

アップグレードは`pip install -U chimera-agent==0.45.1`で行えます。デプロイメント検証には、コンテナで`serve --cron`を実行し、ゲートウェイ初期化メッセージを確認してください。変更の詳細な技術情報は[Chimera Agent v0.45.1](https://github.com/brcampidelli/chimera-agent/releases/tag/v0.45.1)にあります。
