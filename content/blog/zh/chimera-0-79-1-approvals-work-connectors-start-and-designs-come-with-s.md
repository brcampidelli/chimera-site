## 审批为什么出错，现在又如何解决竞态

在这个版本之前，审批一个设计可能会失败，并抛出一条令人困惑的提示：“另一个 Chimera 进程提出了这个问题。”这个错误跟其他进程毫无关系。设计审批本身是作为其专属对话中的一个问题来应答的，答案会同时出现在审批窗口、状态栏和治理列表中。只有拥有者的屏幕才能回答。问题在于，两个几乎同时到达的应答会发生碰撞，而系统无法只记录其中一个并继续运行。这个报错只是噪音，但它阻塞了审批流程，让用户没有明确的恢复路径。

0.79.1 版本正确处理了这种情况。当两个应答同时抵达审批环节时，系统只会记录其中一个——竞态被解决，而不是被拒绝。审批完成，设计继续推进，用户在三个 UI 界面上看到的状态保持一致。任何构建智能体来产出设计并经由人工审批环节流转的开发者，现在都可以信赖这套治理流程，不会再遇到那个本质上跟并发毫无关系的偶发性崩溃。

## 不再空白的设计提案

Chimera Design 有一个更深层的问题：它的首次提案几乎毫无用处。模型会返回一个格式错误的操作，系统抛出一个模型自身无法修复的原始错误，对话就此卡住。即使操作结构上合法，提案本身也只是纯文本——没有排版、没有背景、没有形状。这意味着与 Design 的第一次交互，你要求视觉输出，却得不到任何视觉化的东西。

修复包含四个部分。格式错误的操作现在会返回一个模型能够修复的参数错误，这样对话就能自我纠正，而不是直接中断。每个操作都会展示其预期的形状，给模型一个明确可达成的目标。当提案因为试图在单轮对话中塞入过多操作而被截断时，系统会检测到截断，并用更少的操作重新提问。最后，首次提案默认就会请求排版、背景和形状——输出从第一轮开始就是视觉化的。结果就是，无需手动重试循环，就能得到一个可用的首次提案。

## 能启动的连接器，以及不会撑爆上下文的文件

两项基础设施修复对连接外部工具的用户很重要。第一，Windows 用户通过 `.cmd` 启动器运行连接器时——常见场景是通过 `npx` 连接 Supabase——如果连接器命令的 URL 中包含 `&` 字符，就会静默中断。启动器会错误解析这个字符，命令被截断，连接器永远无法启动。Chimera 现在会拒绝无法安全传递的参数，并告诉你原因，让失败变得明确且可修复。应用也不再等待 MCP 服务器连接成功后才打开界面。以前，在连接器超时期间，UI 可能会卡在“获取失败”的状态长达两分钟。现在服务会立即打开，连接在后台解析。

第二，返回内联音频或图像的连接器——比如 VoiceStudio 的旁白——过去会直接把 base64 数据倾泻到模型上下文中。模型不得不把这些编码后的二进制数据当作文本来读，这会迅速填满上下文窗口并中断当前轮次。现在，这些文件会被保存到项目的 `mcp-output/` 文件夹中，不纳入版本控制，对话中将其引用为可播放或可查看的构件。模型永远不会看到原始字节，当前轮次得以完成，不会耗尽上下文。

## 重启后依然生效的权限状态

“忽略权限”开关现在位于项目级别，并且能在重启后持久化。项目级开关覆盖该项目下的所有对话，包括新建的对话，同时每个对话仍保留自己独立的开关。打开项目开关会立即释放那些已经在等待权限的卡片。重启后，一条横幅会列出每个保存了开关开启状态的项目和对话；你只需点击一次确认即可重新激活它们，其余的则被丢弃。只有桌面端屏幕可以打开这个开关，而关闭它始终会在所有地方生效——安全边界是单向的。

## 现在该做什么

通过 `pip install chimera-agent==0.79.1` 升级。如果你使用 Design，开启一个新提案，检查首次响应是否包含视觉结构。如果你在 Windows 上使用 Supabase 或任何基于 `npx` 的连接器，请验证连接器能否在无需手动转义参数的情况下正常启动。完整发布说明见 [Chimera Agent v0.79.1](https://github.com/brcampidelli/chimera-agent/releases/tag/v0.79.1)。
