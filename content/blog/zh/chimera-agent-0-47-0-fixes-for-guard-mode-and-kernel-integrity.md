## 守护模式现已正确报告拒绝操作

此前，当网关拒绝工具调用时，返回的观察字符串未以`error:`开头，导致系统误记录为成功。这影响三个层面：桌面框架、步骤日志和漂移检测。一个所有危险操作都被拦截的运行过程，会在所有结构化数据中显示为成功，模型甚至会上报从未发生的强制推送等已完成操作。现内核已正确标记拒绝操作，且拒绝文本会指明具体由哪个守护规则触发。

## 修复多行脚本的规则匹配问题

原规则引擎使用`repr`处理脚本文本，导致换行符被转义为两个字符。这会破坏规则模式中的单词边界，引发两个问题：

1. 简单单行脚本可能绕过保护机制，因为`\n`会与后续单词粘连
2. 引用危险命令的Markdown文档会被错误拦截

有两个规则因此问题完全未触发。现文本传递至规则时不再转义，匹配实际脚本行为。

## 审计系统不再存储敏感信息

受管控的`write_file`操作曾将完整文件内容（包括`.env`文件和私钥等敏感数据）存入`audit.jsonl`，即使该操作已被其他守护规则拦截。现审计系统会使用现有脱敏器（原仅用于步骤追踪）对敏感内容进行脱敏，并将文档型参数记录为仅含大小的元数据。

## HTTP端点新增内核可见性

运行、批处理和轮转端点的HTTP响应中此前未包含信任内核的判定结果，导致强制推送审批等关键决策对客户端不可见。当`CHIMERA_GOVERNANCE`设为`observe`或`enforce`时，内核现已正确安装至HTTP接口。注意HTTP部署永远不会在服务器终端弹出提示——该控制台的操作者并非实际请求发起者。

## 其他修复

- 审计链不再误报并发写入导致的篡改
- `observe`模式现准确统计本应仅作测量的拒绝操作
- 卡住的worker不再无限期占用整批任务
- 新增容器资源限制配置功能
- 终端使用新增上下文预算控制

## 已知限制

团队明确记录了当前三个未解决问题而非留待用户发现：

1. `observe`报告尚未在HTTP接口呈现
2. API在`enforce`模式下缺少审批路径
3. 仍有四个HTTP端点未包含内核判定结果

通过`pip install --upgrade chimera-agent`更新，或查看[Chimera Agent v0.47.0](https://github.com/brcampidelli/chimera-agent/releases/tag/v0.47.0)获取详细版本说明。
